SPT 4.1 · Mapeamento de deofuscação

Do GClass2667 ao WeaponMountingComponent

O FireFly falou que o 4.1 "matou as assombrações de GClass". Os arquivos que ele mandou em docs/files-from-4.1/ mostram exatamente o que isso significa — e batem direto com nomes que já estão nos meus próprios mods.

→

Essa é a mesma classe que meu PassiveMountDetectPatch.cs comenta como "caixa-preta" — porque hoje ela não tem nome.

Mecanismo

O que esses 10 arquivos JSON realmente são

Cada categoria de identificador ofuscado do decompilado do EFT ganha seu próprio arquivo de mapeamento Nome-Antigo → NewName. Juntos, os 10 arquivos resolvem ~5.850 identificadores (classes, interfaces, structs, delegates, eventos, exceptions e atributos) — 3.599 só de GClass de nível superior.

O comentário que já documentava o problema

Antes mesmo de ver essa tabela, meu código já tinha uma defesa explícita contra exatamente essa instabilidade:

StanceManager.cs:1138-1144 
// === REFLECTION CACHEADA PARA BACKING FIELDS DE EVENTOS DE GClass774 ===
// Os backing fields são private e foram renomeados pelo decompilador.
// Resolvemos por lista de candidatos: nome público primeiro, nomes do decompilador como fallback.
private static readonly FieldInfo _onValueChangedBacking =
    ResolveBackingFieldByCandidates(typeof(GClass774), nameof(GClass774.OnValueChanged), "action_3");

Com GClass774 virando Stamina de forma estável, esse fallback por candidatos deixa de ser necessário para casos assim — o nome público já não muda de build para build.

Já era um antipadrão conhecido

Isso é o AP-03 do meu próprio spt-antipatterns.md

Meu documento de antipadrões já cataloga esse risco antes de qualquer notícia sobre o 4.1:

AP-03 — Alvo virtual/ofuscado sem auditar overrides

Causa raiz: "alvos ofuscados (GClass####, method_##) resolvidos por nome literal quebram entre builds do EFT."

Prevenção: "resolver alvos ofuscados por assinatura/predicado estável, nunca por nome literal."

A deofuscação do 4.1 não elimina o AP-03 — patches ainda vão precisar validar contra o assembly real —, mas remove a causa mais comum dele: hoje, o número muda de build para build; com nome real, o nome tende a persistir (a assinatura ainda pode mudar, mas o alvo já não é "GClass2667 nesta build específica").

Ressalvas

Antes de confiar nesses arquivos como definitivos

  • Isso não parece um dump oficial da BSG. GStruct-Mappings.json e GInterface-Mappings.json têm comentários manuscritos tipo // Custom, doesn't exist in the 1.0 client anymore e até // Yo dawg I heard you were interested in some nested classes so I put some nested classes in your nested classes — marca de uma base mantida pela comunidade de engenharia reversa ao longo de várias versões do jogo, não uma tabela gerada oficialmente só para o 4.1.
  • Cobertura não é 100%. GClass898 e GClass3008, usados no meu próprio UnderFire-2.0.1/Plugin.cs, não aparecem em nenhum dos 10 arquivos — ou porque nunca foram identificados, ou porque o número já apontava para outra coisa em outra build.
  • A numeração já era instável antes disso. O mesmo GClassNNNN pode referenciar classes diferentes entre builds do EFT — é exatamente o que o AP-03 já alertava. Isso não é um problema novo do 4.1; é o motivo pelo qual o 4.1 estar desofuscando o código é uma boa notícia estrutural.

Na prática

O que isso muda para os meus mods

Quando o 4.1 sair de fato (a FireFly foi clara: ainda falta "muita coisa"), o efeito esperado nos patches que hoje dependem de GClassNNNN/method_## é:

  • Referências como typeof(GClass774) deixam de compilar — precisam virar typeof(Stamina) e similares, em todos os mods que usam esse padrão (stances, UnderFire, TRLTraderPrices, CustomClasses).
  • Fallbacks defensivos como ResolveBackingFieldByCandidates continuam válidos como rede de segurança, mas passam a ser necessários com menos frequência.
  • Os dois casos sem mapeamento (GClass898, GClass3008) são candidatos a checar manualmente contra o assembly real assim que o 4.1 sair — exatamente o antipadrão descrito na seção "decompile parcial" do spt-antipatterns.md.
